# KolobanovEye 2.0 — план реализации и проверок

План ссылается на разделы приложенного ТЗ «KolobanovEye 2.0 — техническое задание для Codex». Статусы означают подтверждение, а не наличие кода. Работы выполняются локально; ресурсы игры и датасет в Git не публикуются (§1–2).

## Этап 0. Совместимость и качество исходной сцены — частично подтвержден

| Требование | Статус и критерий завершения |
|---|---|
| Сборка Dagor на Windows, локальная загрузка Normandy и Tiger с деревом, программный RGB (§2, §4, §13.0 п. 1–6) | Подтверждено логами ke-run-20: 1280×720, 138 нод, текстуры и материалы; GPU-проверка таблицы clipmap mismatches=0. Это подтверждение для конкретных версий, карты и модели. |

| Сопоставление с игрой (§13.0 п. 7) | Ожидается: нужен локальный игровой кадр той же карты и Tiger при близких условиях. Зафиксировать отличия. |

Дополнение: подготовлен ограниченный перебор камеры для каждого кадра (высота и пересечение проекции с кадром). Неудачная попытка не расходует кадр; тест на Windows ожидается. ### 1.3. Размещение техники и камеры (§5–6, §13.1)

- [ ] Пользователь подтвердил измерения: перепад четырёх углов AABB 0.2478 при пороге 0.5. Подготовлен поиск одной позиции для серии с ограниченными попытками по высоте центра и четырёх углов; Windows-проверка ожидается. Вода, уклон, контакт и столкновения не проверяются.
- [ ] Проверка столкновений со статикой и другой техникой на габаритах; оценить доступность статической геометрии (в ke-run-20 `static_collision=0`). При недоступности честно отклонять/помечать непроверенные точки.
- [ ] Ограниченные попытки, отказ не списывает квоту, смена точки при неудачах. Предварительный кэш пригодности и зоны — после проверки базовой геометрии.

Критерий: тестовые валидные/невалидные точки на суше, воде, склонах и у препятствий с журналами причин, плюс визуальная проверка на Windows.

**Вода — следующий приоритет внутри этапа 1 (§5):** В ke-generate-05 сцена сообщила `hasWater=1`, `waterLevel=0`, центр рельефа 55.3856; происхождение и корректность уровня ещё не подтверждены. В исходниках `AcesScene` найдены `hasWater` и `waterLevel`. Значение берётся из `levelSettingsBlk`, при отсутствии поля используется `0`, а тип/границы воды могут быть сложнее плоскости. Добавлено только диагностическое чтение и сохранение исходного уровня; без подтверждения на известных точках суши и воды результат `water_check` остаётся `unknown` и точки не отбрасываются. Далее: установить происхождение настроек и геометрию воды, проверить берег/воду/сушу, внедрить отклонение и повторный выбор кандидата, только после этого обозначить проверку работающей.

## Этап 2. Видимость, сегментация и отрицательные сцены (§8–10, §13.2)

Цель этапа — получить проверяемую разметку танка и контролируемые перекрытия. Работу ведём крупными пакетами; результат каждого пакета можно использовать, не ожидая реализации всех масок.

### 2.1. Базовая точность разметки (§9)

- [ ] Собрать контрольные кадры: разные ракурсы, размеры, частичное обрезание границами кадра, перекрытие и объект за камерой.
- [ ] Сравнить фактическую разметку с ручными эталонами; проверить матрицы, ближнюю плоскость и границы для разных разрешений/FOV.
- [ ] Исследовать доступные геометрические границы частей/нод и ID-проход, убрать избыточность AABB проверенным способом.
- [ ] Хранить метод и область применимости каждого bbox. Нельзя называть 3D-AABB видимым bbox.

**Результат:** отчёт об ошибках и воспроизводимый тестовый набор; улучшенный bbox только после подтверждения.

### 2.2. Proxy перекрытия (§8)

- [ ] Проверить доступность коллизий рельефа и статических объектов на конкретной карте; текущий `static_collision=0` не означает отсутствие препятствий.
- [ ] Создать proxy танка и точки выборки; настраиваемо 100–1000 или обоснованное количество лучей. Проверять пересечения с доступной геометрией.
- [ ] Сохранять `visibility_proxy`, `occlusion_proxy`, число лучей, версию метода и области, которые не покрыты коллизией.
- [ ] Добавить диапазоны перекрытия, квоты и ограниченные попытки. Непроверенные случаи не выдавать за полностью видимые.

**Результат:** диагностические сцены с известными перекрытиями и сравнением с ручной оценкой; proxy не трактуется как точная доля пикселей.

### 2.3. Маски и точные для рендера bbox (§8–9)

- [ ] Исследовать отдельный проход ID и порядок рендеринга при одинаковых камере, LOD и геометрии.
- [ ] Получить бинарную instance visible mask с учётом depth и отдельно amodal mask; обработать несколько экземпляров и перекрытия.
- [ ] Рассчитать `bbox_visible` из видимой маски, `bbox_amodal` из полной; определить пустые и частично обрезанные случаи.
- [ ] Сопоставить маски с RGB на граничных случаях, проверить разрешение и стабильность ID. Маски сохранять без потерь.

**Результат:** проверенная instance-разметка и метрики видимости для конкретного рендера; если ID-проход недоступен, зафиксировать причину и продолжать с явно обозначенной proxy-разметкой.

### 2.4. Части модели (§9)

- [ ] Проинвентаризировать реальные ноды и draw calls выбранных моделей; создать таблицу соответствий `hull`, `turret`, `gun`, `tracks`, `running_gear`, `equipment`, `other`.
- [ ] Поддержать исключения и неизвестные ноды, проверить скрытые/повторные узлы и LOD; не предполагать классификацию по имени без проверки.
- [ ] Получить part ID-маски и визуальные отчёты; протестировать на нескольких моделях.

**Результат:** воспроизводимые instance/part masks и таблица покрытия; не блокирует базовый detection при недоступности.

### 2.5. Негативные сцены и квоты (§3, §10–11)

- [ ] Реализовать кадры без целевой техники с параметром `empty_frame_fraction`; подтвердить фактическое отсутствие танка в сцене.
- [ ] Считать успешные файлы, а не попытки; сохранять причины отказов и распределение пустых/непустых кадров.
- [ ] Сбалансировать размеры объектов и перекрытия по заданным диапазонам, не генерировать незапрошенные модели.

**Результат:** контролируемая доля пустых кадров и статистика, прошедшая проверку целого набора.

### 2.6. Форматы и приёмка (§9, §12–14)

- [ ] Расширить COCO-экспорт для detection/segmentation, сохранить маски в PNG/RLE и расширенные metadata JSONL.
- [ ] Валидировать ID, соответствие изображений/аннотаций, области bbox/mask, отрицательные изображения и отсутствие смешения групп.
- [ ] Выполнить ручную проверку контрольного набора и исследовать mAP/precision/recall после появления пригодных обучающих данных.
- [ ] Сопоставить рендер с игровыми скриншотами, отдельно учесть доменный разрыв.

**Результат этапа:** проверенный небольшой набор с документированным качеством, ограничениями и воспроизводимой командой/интерфейсом. Проверка отдельных пакетов по возможности объединяется в один Windows-запуск.

### Наблюдение на Windows: серия из 400 кадров

Пользователь сообщил, что кадры 000231–000261 тёмные и без танка. В журнале этих кадров есть FRAME_OK и данные камеры, но это подтверждает только сохранение, а не видимость модели. Исходные PNG необходимы для диагностики; до её завершения эти кадры нельзя считать пригодными для обучения. В конфигурации радиус размещения равен 0: все позиции приходятся на одну точку. Новые диапазоны высоты камеры и ускоренная проверка ещё требуют запуска на Windows.

### Размещение по всей карте

Добавлен экспериментальный режим выборки по границам ландшафта с процентным отступом, seed и проверкой кандидатов по высотам. Требуется сборка и проверка на Windows: фактические границы, распределение, работа повтора и результаты на воде/препятствиях. На предоставленных изображениях камера оказалась закрыта листвой: проверка видимости и препятствий остаётся открытой задачей.
