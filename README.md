# KolobanovEye 2.0 · этап 0

Прототип проверяет, сможет ли открытый Dagor загрузить бинарную карту **Normandy** и модель **Tiger H1** из вашей установки War Thunder и сохранить полноразмерный RGB-кадр. Код работы со сценой на C++, команды сборки и запуска на Python. Открытый DaEditorX создаёт контекст DX11, загружает ресурсы через локальную конфигурацию CDK и принимает команду захвата из batch-файла. Во время проверки может быть видно окно. Рендер выполняется в отдельную текстуру. Внутри проекта-запуска нет геометрии, вся геометрия для кадра поступает из установленных ресурсов игры.

**Статус.** На Windows в ke-run-20 получен реальный RGB 1280×720: загружены Normandy и Tiger, таблица clipmap проверена на GPU (`mismatches=0`), пользователь подтвердил исправление земли. Полная визуальная приёмка окружения, материалов и контакта с рельефом, а также сравнение с игрой ещё не проведены. На кадре присутствуют служебные линии. Пакетная генерация одним процессом подтверждена пользователем на Windows; оценка видимости не реализована. В серии из 400 кадров пользователь обнаружил тёмные кадры без танка 000231–000261: причина пока не установлена.

## Экспериментальная разметка и серия кадров

`frame` дополнительно записывает `annotation.json`: класс `tank`, `bbox_xywh` и метод `projected_local_3d_aabb_depth_clipped_and_frame_clamped`. Это приближённая проекция 3D AABB, а не видимый bbox: перекрытие и точность габаритов модели не проверены. Остальные параметры камеры и сцены сохраняются в `frame.blk`. Изображение пока может содержать линии редактора.

Экспериментальная серия (каждый кадр заново запускает редактор и загружает карту; это не пакетный генератор по ТЗ):

```powershell
python .\ke_pilot.py --dagor D:\Projects\DagorEngine --game D:\Games\WarThunder --out D:\Projects\ke-pilot-01 --seed 42 --count 3
```

Скрипт заранее пишет `plan.json`, меняет только yaw и добавляет запись в `metadata.jsonl` после успешного кадра. Воспроизводится план, а побитовая идентичность GPU-кадров не гарантируется. Скрипт и JSON-разметка проверены на Windows в `ke-pilot-01`. Возобновление, геометрические проверки, вариация камеры и погоды не реализованы.

## Один процесс для нескольких кадров (эксперимент)

После обновления кода необходим повторный `build --ooz`: новый C++ патч выполняет цикл кадров после однократной загрузки карты и модели. Команда запуска:

```powershell
python .\kolobanoveye.py frame --dagor D:\Projects\DagorEngine --game D:\Games\WarThunder --out D:\Projects\ke-sequence-01 --seed 42 --count 3 --clipmap-feedback software
```

В `images/` ожидаются кадры, `metadata.jsonl` содержит аннотации и метаданные, `plan.json` — seed, фиксированный yaw танка и азимуты камеры. Камера перемещается относительно центра модели, а танк остаётся на месте. Рабочий каталог и логи создаются один раз на запуск. Параллельные процессы не используются. Камера выбирает азимут 360° и горизонтальную дальность. В CLI доступны угол возвышения `--camera-elevation-range MIN MAX` либо высота над локальным heightmap `--camera-height-range MIN MAX`; в окне используются расстояние и высота. Вариант с высотой требует проверки на Windows. Проверка высоты камеры над heightmap имеется, проверка препятствий пока не реализована. Кадры PNG ещё не сжимаются в JPEG/WebP. При сбое журнал и уже записанные PNG остаются для диагностики, продолжение не реализовано. `SEQUENCE_BEGIN ... map_loads=1 model_loads=1`, несколько `FRAME_OK` и `SEQUENCE_OK` в журнале требуются для проверки. Серия в одном процессе подтверждена пользователем на Windows; орбитальная камера после следующей пересборки ещё требует проверки.

### Просмотр рамок

После получения серии можно создать отдельные диагностические копии с зелёной рамкой:

```powershell
python .\ke_review.py --run D:\Projects\ke-clean-01 --out D:\Projects\ke-review-01
```

Исходные RGB не изменяются. Рамка показывает проекцию 3D AABB, может быть заметно больше силуэта и не измеряет видимость. Отчёт `report.json` включает положения танка и камеры. Для одиночного кадра этот просмотр пока не предназначен. На время снимка редакторский проход `renderObjects`/`renderTransObjects` отключается: это должно убрать сетку, но новый код и сохранность остального содержимого требуют проверки Windows.

Пример более широкого диапазона ракурсов (указывается новая выходная папка):

```powershell
python .\kolobanoveye.py frame --dagor D:\Projects\DagorEngine --game D:\Games\WarThunder --out D:\Projects\ke-orbit-varied-01 --seed 42 --count 6 --camera-distance-range 18 35 --camera-elevation-range 10 25 --clipmap-feedback software
```

План хранит интервалы и параметры каждого ракурса. Повтор с таким же seed и конфигом воспроизводит план, а не гарантирует побитовую идентичность GPU-кадров. Для каждого кадра заранее создаются варианты камеры; неудачная проверка не расходует запрошенный кадр. При исчерпании лимита попыток серия прерывается. Размеры объекта по пикселям сейчас не планируются и пересечения со статическими объектами не проверяются.

### Проверка высоты

После пересборки каждый кадр проверяет высоту камеры над heightmap (порог `--camera-clearance`, по умолчанию 0.5 единицы); если высота не найдена или камера ниже порога, для того же кадра пробуется следующий ракурс до заданного лимита. В `frame.blk` или `metadata.jsonl` сохраняются `camera_ground_y`, `camera_clearance` и количество измерений у четырёх нижних углов 3D AABB; минимум и максимум записываются при наличии измерений. Проверка не выявляет воду, препятствия или реальный контакт гусениц. Новый код требует проверки на Windows.

Линии на земле сохраняются даже после отключения editor overlays. Они видны также в `static-albedo` ранней диагностики, до отрисовки танка; источник пока не установлен.

Подробные этапы, критерии и ссылки на ТЗ приведены в [PLAN.md](PLAN.md).

## Окно настроек Tkinter (эксперимент)

После сборки проекта запустите из каталога проекта:

```powershell
python .\ke_gui.py
```

Окно настраивает пути, число кадров (2–1000), seed, размер, FOV, область размещения и поворот танка, диапазоны горизонтального расстояния до танка и высоты камеры над местным рельефом, а также таймаут. Новая настройка высоты требует пересборки Dagor и проверки на Windows. X/Z — центр области поиска на карте; радиус 0 оставляет танк в этой точке. Минимальный зазор — отдельный защитный порог над heightmap. Карта Normandy и Tiger H1 зафиксированы. Выберите **родительскую** папку результатов и нажмите «Создать и проверить датасет». Программа выбирает свободную папку `ke-generate-01`, `ke-generate-02` и т. д., затем последовательно выполняет рендер, проверку, диагностику рельефа и экспорт COCO в подпапку `coco`. Диагностика записывает `terrain-report.json`: перепад по четырём углам 3D AABB сравнивается с порогом 0.5, а вода, препятствия и контакт остаются неизвестными. Она не отклоняет сцену и не меняет позицию танка. Отдельные операции и настройки находятся в меню «Дополнительно», объяснения — в кнопке «? Справка». После успешной работы кнопка «Открыть папку» открывает результат в Проводнике Windows. «Копировать журнал» копирует выделенный фрагмент или весь журнал. Настройки пишутся в `generation-config.json` в каталоге запуска. Лог движка собирается в папке результата; окно не отображает покадровый прогресс в реальном времени. Нельзя закрывать окно, пока операция выполняется.

Те же параметры можно запустить без окна (этот путь выполняет только рендер; проверка и экспорт вызываются отдельно):

```powershell
python .\ke_generate.py --config .\config.example.json
python .\ke_validate.py --run D:\Projects\ke-generate-01
```

Перед запуском измените выходную папку в JSON, если она уже существует. Валидатор проверяет план, количество, файлы RGB, их контрольные суммы PNG и границы bbox; он не измеряет видимость и качество разметки. Обновлённая группировка интерфейса и настройка высоты ещё требуют проверки на Windows. При исчерпании попыток места или камеры последовательность прерывается; автоматического продолжения после сбоя пока нет. Погода, несколько моделей и карт пока не настраиваются.

## Поза башни и орудия Tiger H1

В секции «Танк и место» GUI доступны диапазоны углов. JSON принимает `turret_yaw_min` / `turret_yaw_max` и `gun_pitch_min` / `gun_pitch_max`. В CLI `frame` используйте `--turret-yaw-range -90 90 --gun-pitch-range -4 10`. При разных границах нужен seed. Равные границы задают фиксированное смещение относительно исходной позы. Нулевые диапазоны сохраняют исходную позу. Башня поворачивается относительно корпуса, положительный наклон поднимает дуло. Допустимые для пробного режима интервалы: башня ±180°, наклон −8…+15°. Проверка взаимодействия модели с корпусом и рельефом в этих позах остаётся задачей.

При включённой позе углы выбираются отдельно для каждого кадра. Лог `TANK_POSE`, BLK, JSONL и COCO содержат применённые значения. Рамка учитывает консервативную габаритную оболочку и может быть шире силуэта. Поддерживается Tiger H1 со штатным скелетом. Серия из шести кадров с разными позами и успешным экспортом COCO подтверждена на Windows (PR #3). Для запуска требуется сборка Dagor с патчем артикуляции.

## Адаптивный прогрев перед сохранением кадра

Пересоберите Dagor командой `python .\kolobanoveye.py build --dagor D:\Projects\DagorEngine --ooz D:\Projects\ooz`. Сборщик обновляет исходники на закреплённом коммите Dagor и распознаёт уже установленные патчи прогрева.

Генерация из JSON, GUI и команда `frame` по умолчанию ждут стабильности изображения. После `min_warmup_renders` (по умолчанию 8, допустимо 8–64) движок измеряет изменение RGB по сетке 16×9 каждые четыре прохода неподвижной камеры. Для сохранения нужны три последовательные успешные проверки и готовность карты, текстур и освещения. Режим ждёт до 20 секунд на прогрев кадра и завершает захват ошибкой, если критерий не достигнут. Проверки записываются как `FRAME_STABILITY` и `FRAME_STABILITY_FINAL`. Измерение может синхронизировать CPU и GPU и увеличить время генерации.

Для контрольного прогона задайте `"wait_frame_stability": false` в JSON, снимите флажок «Ждать стабильности изображения» в GUI или передайте `--no-wait-frame-stability` команде `frame`. Явное значение `false` в ранее сохранённых конфигурациях сохраняется. Опциональный `wait_sky_convergence` проверяет сходимость освещения неба даже при отключённой проверке RGB. Прогрев не изменяет настройки атмосферного тумана.

Метод стабилизировал проблемные ракурсы и прошёл проверку 40 кадров на Windows в исследовательской ветке. Сценарии сравнения кадров и изоляции эффектов остаются в [fix/resolve-white-haze](https://github.com/ElecTriKusX/KolobanovEye/tree/fix/resolve-white-haze).

## Экспорт в COCO (эксперимент)

Основная кнопка автоматически экспортирует COCO в `coco/all.json`; отдельный экспорт доступен через «Дополнительно → Экспортировать COCO отдельно». Кадры не копируются: пути к оригинальным PNG относительны папке экспорта. Переносить результат отдельно от исходных кадров нельзя. Экспорт и кадры должны находиться на одном диске. Рамки — приближённые проекции 3D AABB, видимость не проверена; их пригодность для обучения нужно оценить.

Для нескольких серий и разбиения по участкам:

```powershell
python .\ke_coco.py --runs D:\Projects\ke-run-a D:\Projects\ke-run-b D:\Projects\ke-run-c --out D:\Projects\ke-coco-01 --split --tile-size 256 --seed 42
```

Потребуются минимум три различные группы по карте и координатной ячейке; углы камеры, yaw и seed не разделяют группу. `train.json`, `val.json`, `test.json` и `manifest.json` записываются в новую папку. Группировка по ячейкам не устраняет близость соседних сцен по обе стороны границы; отдельные карты и буферные зоны потребуют дополнительного контроля. Экспорт с путями к изображениям ещё нужно проверить на Windows и в целевом ML-фреймворке.

### Диагностика воды (эксперимент)

После сборки журнал содержит `WATER_PROXY`: признак наличия водной плоскости и значение `AcesScene::waterLevel`, если `hasWater` установлен. В метаданных и `terrain-report.json` сохраняются `water_plane_y` и разность высоты центра рельефа относительно плоскости, когда они доступны. `water_check` остаётся `unknown`: значение могло прийти из настроек по умолчанию, а водоём может быть ограничен или устроен иначе. Для установления метода нужны известные точки суши, воды и берега и проверка геометрии; отбраковки по воде пока нет.

## Размещение по всей карте

В окне режим «Вся карта» выбирает точки по прямоугольным границам загруженного ландшафта Dagor (`LandMeshManager::getBBox`). «Отступ от краёв карты, %» применяется к каждой стороне отдельно; по умолчанию 15%. Кандидаты и ракурсы воспроизводятся по seed. Точки проверяются по heightmap, но вода, здания, деревья и видимость танка не проверяются: пригодность кадров необходимо контролировать. Границы ландшафта не гарантируют совпадение с игровыми границами и проверяются на конкретной карте. После смены кода нужна пересборка Dagor; режим ещё требует запуска на Windows.

Выберите «Вокруг точки», чтобы использовать координаты X/Z и радиус поиска. Это позволяет явно выбрать (0, 0); радиус 0 фиксирует положение. В `plan.json` кандидаты режима всей карты заданы как нормализованные координаты от 0 до 1, а фактические границы и позиция сохраняются в метаданных кадра и журнале `MAP_BOUNDS`. При отсутствии допустимой точки после установленного числа попыток запуск завершается ошибкой.

## Несколько позиций за один запуск

В окне задайте общее число кадров, режим размещения и число «Кадров на позицию». Например, 6 кадров и 2 на позицию создают план трёх позиций, по два ракурса для каждой. Поиск каждой позиции независим и воспроизводим по seed; это проверка только heightmap. `composition_index` и выбранный кандидат сохраняются в метаданных. Карта и модель загружаются один раз. В случае исчерпания попыток позиции или камеры серия прерывается: автоматическое возобновление не реализовано. Новая реализация требует сборки и проверки на Windows.

## Экспериментальный поиск места

После повторного `build --ooz` можно установить в окне «Радиус поиска точки» больше нуля, «Попыток размещения» и «Макс. перепад высот». X/Z задают центр области, seed — список случайных кандидатов. Dagor загружает карту и модель один раз, проверяет центр и четыре нижних угла габарита по heightmap и выбирает первый кандидат с допустимым перепадом. Число ракурсов на одну позицию задаётся параметром «Кадров на позицию». После него выбирается следующая позиция, сохраняя загруженными карту и модель. Радиус 0 оставляет все позиции в заданной точке.

Если ни один кандидат не прошёл, запуск завершается ошибкой `PLACEMENT`; попытки логируются в `probe.dcmd.log`. Запись `PLACEMENT_OK` обозначает только проверку heightmap. Вода, коллизии со статикой, контакт гусениц, наклон и проверка камеры на препятствия не реализованы. Если камера не прошла проверку высоты или проекции, для текущего кадра выбирается следующий запланированный ракурс; если лимит попыток исчерпан, серия прерывается. На Windows этот вариант ещё не проверен.

## Восстановление после сбоя (диагностика)

В меню «Дополнительно → Восстановить метаданные после сбоя» выберите папку прерванной серии. Либо выполните `python .\ke_recover.py --run D:\Projects\ke-generate-01`. Скрипт проверяет уже записанные пары PNG/BLK и пишет `metadata.recovered.jsonl` и `recovery-report.json`; существующие кадры и временные BLK не изменяются. Он не продолжает рендер, не создаёт итоговый COCO и не считает прерванную серию завершённой. Восстановление повторно не перезаписывает отчёты. Поддерживаются планы schema 3 с номерами композиций; Windows-проверка ещё требуется.

## Сборка под Windows x64

Понадобятся Git, Python 3.10+, 7-Zip и официальный toolchain Dagor. В `make_devtools.py` описаны требуемые Visual Studio и Windows SDK. Для запуска нужен рабочий DX11-драйвер и активная рабочая сессия Windows. Используйте короткие пути латиницей без пробелов для checkout, toolchain, установки игры и папки результатов. Распакуйте этот архив, например в `D:\dev\KolobanovEye_2.0_phase0`.

В PowerShell из папки `D:\dev`:

```powershell
git clone https://github.com/ElecTriKusX/DagorEngine.git
git -C .\DagorEngine checkout --detach 9639942de5a8e5b01d91977f60ed82cda22d5f41
Set-Location .\DagorEngine
py -3 .\make_devtools.py D:\dev\devtools
```

Скачайте [tools-base.7z](https://dagorenginedata.cdn.gaijin.net/head-2026.11.07/tools-base.7z) из README зафиксированного коммита и распакуйте его в корень **открытого** `D:\dev\DagorEngine`. Каталог `tools\dagor_cdk\commonData` должен содержать `guiShaders.ps40.shdump.bin`. Откройте новый PowerShell после установки toolchain. Если путь к Jam не задан глобально, добавьте его в текущую сессию.

```powershell
$env:Path = "D:\dev\devtools;$env:Path"
Set-Location D:\dev\KolobanovEye_2.0_phase0
```

`build` проверяет коммит, проверяет и применяет патчи по порядку и запускает два Jam-таргета x64/dev. Его можно запускать повторно на том же checkout. Код возврата 1 означает ошибку в `inventory.json`. Этот шаг не открывает архивные payload, не строит сцену и не подтверждает совместимый рендер.

## Один кадр

```powershell
py -3 .\kolobanoveye.py frame --dagor D:\dev\DagorEngine --game D:\Games\WarThunder --out D:\dev\ke-run-01
```

Для каждой попытки задайте новый `--out`. Если CDK расположен отдельно, укажите `--cdk` с путём к каталогу, где находится `application.blk`. В штатной конфигурации CDK относительные пути к игре рассчитаны на вложение в `WarThunder\WarThunderCDK`, поэтому внешний каталог должен использовать конфигурацию с корректными локальными путями.

`dumpGrp -dumpR` сохраняет имена и классы ресурсов в `grp.txt`. Если в пакете несколько подходящих вариантов, укажите найденные имена через `--model` и `--skeleton`. Второй параметр также принимает имя `GeomNodeTree` из другого зарегистрированного пакета. Для многоузловой модели требуется корректное дерево и его соответствие именам render nodes.

По умолчанию проверяется точка `X=0, Z=0` на Normandy. Камера смотрит с заданного смещения на центр габаритов. Это пробная композиция. Для смены координат используйте `--tank-xz X Z`, `--eye X Y Z` в мировых координатах, `--yaw` и `--fov` в градусах. `--width` и `--height` задают разрешение, по умолчанию 1280×720. Программа создаёт `capture.blk` с фактическими параметрами. Файлы игры и оригинальные бинарники CDK берутся по локальным путям. Сборка, служебный workspace и выходные данные лежат вне установки игры. Скрипты `setup.cmd`, `dagored.cmd` и `missioned.cmd` из CDK для этого запуска не нужны.

Для разбора ошибки достаточно вывести `inventory.json`, `grp.txt` и сообщения вокруг первого сбоя из журналов. Сами игровые пакеты и кадр можно оставить локально.

При успешном захвате `frame.blk` содержит мировое положение танка и камеры, FOV, глубину отсечения, LOD и `bbox_amodal_aabb_xywh`. Это приближение полной проекции 3D-габарита, обрезанное по границам кадра. Видимость проверяется по изображению. Попадание статической геометрии в луч к центру логируется отдельно и не используется для вычисления bbox. Форматы COCO, маски, случайное размещение и пакетный датасет относятся к следующим этапам.

## Диагностика рендера

Добавьте `--render-debug` к команде `frame`. В подпапке `render-debug/000000/` для первого кадра (и в отдельных папках для остальных) появятся:

- `static-albedo.png` с первым цветовым буфером G-buffer после непрозрачной
  статической геометрии. Он включает рельеф и другие статические объекты.
- `static-depth-mask.png` с белыми пикселями, где статическая геометрия
  записала глубину. Чёрные пиксели соответствуют пустому фону.

Цвет и глубина снимаются до отрисовки танка. Сравните их с `frame.png`.
Если глубина есть, а цвет земли отсутствует уже в G-buffer, проверяйте
материалы рельефа и генерацию clipmap. Если цвет в G-buffer есть, проверяйте
освещение и постобработку. Строки `[KE] RENDER_DEBUG` в `.logs` показывают
статус записи, покрытие глубиной и наличие ресурса шейдера травы
`grass_color_tex`. Сам проход объёмной травы зависит от выбранного рендерера.

В DX11 строки `[KE] CLIPMAP_TILE` показывают мировые границы первого
обновлённого тайла ландшафта под камерой и долю ненулевых RGB-пикселей в двух
точках. `render_buffer` измеряется сразу после растеризации материала,
`cache` после записи того же тайла в атлас. Нулевой RGB уже в первом замере
указывает на рендер тайла. Ненулевой RGB в первом замере и нулевой во втором
указывает на запись в кэш. Если оба замера ненулевые, проверяйте выбор
тайла и его сэмплирование в итоговом проходе. Сверяйте `mip` и границы
тайла с положением камеры. Замер покрывает один тайл и поддерживает
форматы RGBA8 и BC3 (DXT5).

Для сравнения участков Normandy используйте `frame --tank-xz X Z --render-debug`.
Например, снимите `0 0`, `128 64` и `-96 160` в отдельные каталоги.
Камера по умолчанию следует за моделью, высоту модель получает из heightmap.
Оставьте одинаковые FOV и yaw, затем сравните грунт в `static-albedo.png`
и в итоговом кадре. DaEditorX обновляет лучи текущей камеры перед непрозрачным
проходом, где шейдер heightmap восстанавливает мировые координаты.

## Ограничение текущего запуска War Thunder

DaEditorX запускается с DX11 и доходит до `[KE] MAP_BEGIN`. В блоке `TEX` карты Normandy чтение `avg_normandy_lightmap` вызывает `OodleLoadCB::open`. В сборке без Oodle эта функция попадает в `oodleIoStub.cpp`. В журнале также видны такие ошибки на нескольких DDSx-пакетах. Успешный `inspect` подтверждает сигнатуры и версии контейнеров, а для содержимого нужно отдельное декодирование.

Зафиксированный Dagor ожидает авторизованный Oodle SDK **2.7.6** для динамического `daKernel-dev.dll` на Windows x64. В каталоге toolchain `oodle.2.7` Jam проверяет маркер `oodle2_version_2.7.6`, включает `include/oodle2.h` и линкует `static_lib/oo2core_win64.lib`. Если полный `build` также пересобирает статический `dumpGrp`, для него отдельная ветка Jam ожидает SDK **2.9.2** в `oodle.2.9`. Если `dumpGrp` уже собран и читает каталог, можно отдельно пересобрать динамический `daKernel` и DaEditorX штатными Jam-таргетами. Успешную загрузку с SDK ещё предстоит проверить. [Правила сборки Oodle в Dagor](https://github.com/ElecTriKusX/DagorEngine/blob/9639942de5a8e5b01d91977f60ed82cda22d5f41/prog/engine/ioSys/jamfile)

## Почему этот хост

| Задача | Код и границы проверки |
| --- | --- |
| Бинарный уровень | `AcesScene::loadLevel` вызывает `load_binary_dump`. Публичная версия ожидает заголовок `DBLD/3x64`. Общий загрузчик читает текстуры, `SCN`, `ENVI` и внешние включения. `AcesScene::bdlCustomLoad` добавляет `lmap`, `HM2`, `RIGz`, статические коллизии `FRT/SCol` и другие подсистемы. |
| Размещение и коллизии | `getHeightmapAtPoint` запрашивает высоту и нормаль. `tracerayNormalizedStaticScene` проверяет статическую коллизию. Наличие некоторых коллизий не гарантирует полноту препятствий карты, воды или игровой физики. |
| Пакеты | `initPlugins` использует `application.blk`, VROMFS, `resPacks.blk`, `dynModelDesc.bin`, `riDesc.bin` и относящиеся к установке патчи. Версии GRP и DDSx заголовков проверяются отдельно от фактической загрузки. |
| Модель | `get_one_game_resource_ex` разрешает типизированные ресурсы. `DynamicRenderableSceneInstance` выбирает LOD и проходит в штатные стадии deferred-рендера. Поза строится по локальному `GeomNodeTree`. CDK-шейдеры и список доступных материалов определяют фактический внешний вид. |

| Окружение | `ISkiesService::setWeather` и `overrideWeather` поддерживают пресеты и параметры окружения. Проект-запуск запрашивает `day/clear`. Какой свет и погода реально получатся, зависит от BLK и VROMFS. Дождь, туман и вариации параметров на этом этапе не подтверждены. |

## Сборка с ooz и проверка Normandy без Oodle SDK

На Linux адаптер и декодер были скомпилированы вместе с тестовым
`IGenLoad`, который возвращал данные порциями. Все шесть файлов
`testdata/dickens.*` из upstream дали 10 192 446 байт и одинаковый
SHA-256 `b24c37886142e11d0ee687db6ab06f936207aa7f2ea1fd1d9a36763c7a507e6a`.
Проверены чтение, пропуск байтов, повторное открытие и отказ при коротком
входном потоке. Для повтора из корня KolobanovEye под Linux x86-64 с g++:

```sh
git -C /path/to/DagorEngine apply /path/to/KolobanovEye/engine/patches/dagor-ooz.patch
python tests/ooz_linux.py --dagor /path/to/DagorEngine --ooz /path/to/ooz
```

Если патч уже применён, начните со второй команды. Линковку Windows и
игровые пакеты нужно проверить отдельно.

Для этого режима нужен локальный Git checkout [powzix/ooz](https://github.com/powzix/ooz) на коммите
`05038060aa68f9187ae9923b2388ca8db40e58d1` и уже собранный Windows x64 `dumpGrp-dev.exe`.
Откройте **Developer PowerShell for VS** с целевой архитектурой **x64**. В нём должны быть
доступны `cl.exe`, `lib.exe` и установленный Windows SDK. Выполните команды из каталога
KolobanovEye, обновлённого с GitHub.

```powershell
$env:Path = "D:\Develop\devtools;$env:Path"
git -C D:\Projects\ooz rev-parse HEAD
python .\kolobanoveye.py probe-ooz --game D:\Games\WarThunder --ooz-exe D:\Projects\ooz\x64\Release\ooz.exe
```

`probe-ooz` читает DDSx из вложенного блока `TEX` в `avg_normandy.bin`.
Он выводит смещение, размеры, первый тип потока и параметры текстуры. Для обычной
2D-текстуры PC сверяет сумму размеров mip-уровней с DDSx. Когда разбор квантов
показывает, что Oodle-поток заканчивается раньше блока DDSx, тест передаёт
декодеру только байты этого потока и выводит `decoder_input_bytes` и
`tail_prefix_hex`. Скрипт проверяет длину результата и печатает
`OOZ_LIGHTMAP_OK` с SHA-256. Временные файлы удаляются, карта открывается
только для чтения. Успешный тест покрывает одну lightmap.

Если `ooz.exe` возвращает `decompress error` для Leviathan, можно проверить
тот же поток через CLI Rust-декодера `oozextract` 0.5.7. При установленном
Rust/Cargo выполните в PowerShell:

```powershell
cargo install oozextract --version 0.5.7 --locked --features cli,verbose_errors --root D:\Projects\ke-decoders
python .\kolobanoveye.py probe-ooz --game D:\Games\WarThunder --unoodle-exe D:\Projects\ke-decoders\bin\unoodle.exe
```

JSON содержит число крупных квантов и смещения перезапуска декодера
относительно начала Oodle-потока. `decoder=unoodle` в `OOZ_LIGHTMAP_OK`
подтверждает распаковку Rust-декодером. Для запуска кадра с этим декодером
понадобится отдельная интеграция с Dagor. `build --ooz` выбирает C++ `ooz`.

Если `rev-parse` вернул ошибку или другой коммит, подготовьте отдельный checkout
и передайте `--ooz D:\Projects\ooz-src` в команду сборки ниже. Для
`probe-ooz` можно использовать уже собранный `ooz.exe`.

```powershell
git clone https://github.com/powzix/ooz.git D:\Projects\ooz-src
git -C D:\Projects\ooz-src checkout --detach 05038060aa68f9187ae9923b2388ca8db40e58d1
```

После `OOZ_LIGHTMAP_OK … decoder=ooz` выполните:

```powershell
python .\kolobanoveye.py build --dagor D:\Projects\DagorEngine --ooz D:\Projects\ooz
```

Скрипт применяет `engine/patches/dagor-ooz.patch`, собирает локальную x64-библиотеку
декодера и запускает Jam только для DaEditorX с его зависимостями, включая
динамический `daKernel`. Локальная сборка `ooz` завершает декодирование
после получения объявленного числа распакованных байтов. Загрузчик Dagor
потребляет весь объявленный сжатый блок, включая байты после потока, чтобы
следующее чтение началось на границе блока. Журналы — `build-logs\ooz-compile.log`,
`build-logs\ooz-lib.log` и `build-logs\editor-ooz.log`. В последнем должна быть
строка `Building daKernel with the decode-only ooz backend`. Флаги Jam этого
режима — `-sUseOoz=yes` и `-sOozLib=<абсолютный путь к ke-ooz.lib>`.
Обычный `build` сохраняет штатный выбор SDK или заглушки. Jam по-прежнему
сообщает об отсутствующей или неполной версии SDK по своим штатным правилам.

```powershell
python .\kolobanoveye.py frame --dagor D:\Projects\DagorEngine --game D:\Games\WarThunder --out D:\Projects\ke-run-03 --model pzkpfw_VI_ausf_h1_tiger --skeleton pzkpfw_VI_ausf_h1_tiger_skeleton
```

При ошибке сохраните вывод `probe-ooz`. Если он успешен, приложите первый сбой из
`editor-ooz.log` либо из журнала `debug` под `ke-run-03\.logs`. Запись
`FRAME_WRITTEN` и визуальная проверка `ke-run-03\frame.png` подтверждают
получение кадра.

`ooz` читает Kraken, Mermaid/Selkie, Leviathan, LZNA и Bitknit. Поддержка
контрольных сумм Oodle quantum отсутствует в upstream. Backend отклоняет такие
потоки и возвращает ошибку на вызовах сжатия. Потоковый интерфейс Dagor
распаковывает блок целиком при первом чтении или положительном `seekrel`.
Лимит — 256 МиБ отдельно для входа и выхода. У каждого буфера дополнительно
выделяется 64 байта для доступа SIMD на границе. Upstream прямо предупреждает,
что декодер не fuzz-safe. Проверка заголовков и размеров не делает
безопасными произвольные повреждённые потоки. Этот режим рассчитан на
ресурсы доверенной локальной установки.

Код декодера `ooz` распространяется по GPL-3.0-or-later. Скрипт берёт
исходники из указанного checkout, готовит локальную копию без CLI, добавляет
проверку отказа выделения памяти, исправляет индексирование двумерной
таблицы LZNA и явно отклоняет флаг контрольных сумм.
В репозиторий входят адаптер и скрипт, а исходники декодера и собранный с ним

## Диагностика рендера

`ke_diagnose.py` запускает кадр с диагностикой или анализирует существующий каталог, в том числе после неудачного запуска. Дополнительные пакеты Python не требуются. Игра используется только для чтения. Для нового запуска требуется новая папка `--run`.

```powershell
python .\ke_diagnose.py --capture `
  --run D:\Projects\ke-diagnostic-01 `
  --dagor D:\Projects\DagorEngine `
  --game D:\Games\WarThunder `
  --ooz-exe D:\Projects\ooz\x64\Release\ooz.exe
```

Без `--capture` анализируется предыдущий каталог. Пример: `python .\ke_diagnose.py --run D:\Projects\ke-run-15 --dagor D:\Projects\DagorEngine --game D:\Games\WarThunder`. Для другой позиции добавьте `--tank-xz 128 64`; `--indirection cpu` включает экспериментальную CPU-запись. `--ooz-exe` запускает отдельную проверку одного блока lightmap и является необязательным.

Результат: `diagnostics\report.md`, `report.json` и `diagnostics.zip`. Архив содержит логи, параметры и изображения, но не содержит игровых архивов. В нём могут присутствовать локальные пути и сведения о системе; просмотрите перед отправкой. Анализ показателей пикселей охватывает весь кадр, а не маску земли. Успешное чтение глобальных shader variables не подтверждает фактическое состояние GPU-регистров или совместимость шейдеров. Для GPU-захвата нужен отдельный графический отладчик.

### Сравнение пикселей проходов

`python .\ke_pixel_debug.py --run D:\Projects\ke-run-15 --point 600 35 --point 600 300` создаёт `diagnostics\pixel-report.json` и `pixel-grid.csv`, сравнивая сохранённый albedo и итоговый RGB по сетке и выбранным экранным координатам. Размеры кадров должны совпадать. Пороговые подсчёты и средние значения описательные: это разные проходы/моменты, возможны разные цветовые пространства, объекты, оверлеи и экспозиция. Нет сегментации земли. Исходные нормали, освещение и GPU-регистры из этих PNG восстановить невозможно; отсутствующие проходы отмечаются в отчёте.

### Захват буферов вокруг deferred resolve

После `build` и `frame --render-debug` папка кадра, например `render-debug/000000/`, содержит `resolve-input-mrt0.png`, `resolve-input-mrt1.png` и другие доступные MRT, а также `resolve-output.png`, если форматы поверхности поддерживаются. Это снимки до и сразу после `resolve` одного прохода. `PASS_CAPTURE` в журнале сообщает формат и статус каждого файла. PNG для 10-битного формата содержит масштабированные в 8 бит значения; MRT1 — сырая упаковка, её нельзя считать декодированной картой нормалей. Выход resolve — освещённый цвет, не отдельная карта освещения. Нет гарантии одинаковых цветовых пространств.

`python .\ke_pixel_debug.py --run D:\Projects\ke-run-16 --resolve --point 600 35 --point 600 300` сравнивает именно эти два прохода. `ke_diagnose.py` включает сохранённые проходы в архив. Для просмотра реальных shader bindings и исполнения нужны отдельный GPU capture и воспроизведение на целевом Windows; этот код не создаёт RenderDoc capture.

### Открытый DaEditor и RenderDoc

`ke_diagnose.py --capture --keep-open ...` оставляет окно редактора открытым после команды захвата, без таймаута; закройте окно вручную, после чего записывается диагностический отчёт. Режим экспериментальный: работа окна и закладок зависит от конфигурации CDK. При добавлении `--renderdoc-cli "C:\Program Files\RenderDoc\renderdoccmd.exe"` процесс запускается под RenderDoc: после загрузки нажмите в активном окне настроенную клавишу захвата (обычно F12), затем закройте редактор. `.rdc` сохраняется рядом с результатом, не входит в `diagnostics.zip` и может быть большим. Захват вручную не гарантирует нужный draw call; проверяйте наличие сцены и кадров в RenderDoc. Не запускайте игровой клиент. Требуется установленный RenderDoc, интеграция не проверена на целевом Windows.

Формат `R11G11B10F` сохраняется как диагностический `resolve-output.png`: float-каналы обрезаются к [0,1] и квантуются до 8 бит без tone mapping или конвертации цветового пространства. Это не точное HDR-изображение.

### Трассировка DX11 для clipmap и земли

`ke_diagnose.py --capture --keep-open --dx11-trace ...` записывает состояние DX11 во время заполнения indirection и отрисовки земли. В журнале `DX11_FILL_REQUEST` и `DX11_TERRAIN_REQUEST` отмечают положение камеры. Первые восемь обычных и индексированных вызовов в каждом выбранном проходе печатают фактические RTV, viewport, PS и слоты SRV. Если D3DReflect прочитал метаданные, журнал также содержит ожидаемые типы текстур и выходов шейдера. Трасса ограничена первыми четырьмя обновлениями таблицы и шестью позициями камеры. Новая позиция выбирается при перемещении на 128 единиц от предыдущего замера.

Посмотрите землю при загрузке, затем перелетите в область с повторяющимся рисунком и закройте окно. `diagnostics.zip` сохранит полный журнал. RenderDoc для этой трассы не требуется. Трасса содержит состояние привязок на момент вызова DX11. Для покомандного воспроизведения кадра и исполнения пиксельного шейдера нужен отдельный GPU-захват.


### Совместимость таблицы clipmap с War Thunder CDK

В запуске №19 шейдер из `WarThunderCDK/tools.ps50.shdump.bin` выводил `float4` в `SV_Target0`, а движок привязывал `R16_UINT`. Конфликт совпадает с переходом Dagor в `9639942`: прежняя версия читала нормализованные цветовые каналы из `A8R8G8B8`, новая читает упакованный `uint`. Теперь `frame` и `ke_diagnose.py --capture` по умолчанию выбирают `--clipmap-abi legacy-color`, который восстанавливает прежнее побайтовое представление X/Y/mip и формат таблицы. `--clipmap-abi native-int` выбирает современный формат для соответствующего набора шейдеров. По умолчанию таблицу заполняет GPU.

Для проверки после пересборки ищите `CLIPMAP_ABI storage=legacy-color` и `INDIRECTION_CHECK source=gpu ... mismatches=0` в журнале. В режиме `--keep-open` проверьте начальную позицию и перелёт в область, где повторялись тайлы.


## Защита от размещения ниже уровня воды Normandy

В окне «Минимальная высота земли Y» задаёт порог для heightmap. По умолчанию 0.5: измеренный пользователем уровень воды Y=0 плюс запас 0.5. Центр и четыре угла основания габарита должны быть не ниже порога; иначе выбирается следующий кандидат, а при исчерпании попыток запуск завершается ошибкой. Причина `below_water_threshold` и порог записываются в журнал, `minimum_ground_y` — в метаданные. Это консервативный фильтр высоты, не определение границ всех водоёмов и не проверка воды на высоте более 0.5. При выборе другого порога пользователь отвечает за соответствие карте. Необходимы пересборка и проверка Windows.


## Обзорная текстура и координаты в COCO

Включите **Дополнительно → Сохранить обзорную текстуру карты** (`--capture-last-clip` в CLI). В каждой серии PNG доступен по пути `ke-generate-NN/maps/avg_normandy.png`. Для следующих серий используется кэш `.ke-map-cache` в папке результатов. На файловой системе с поддержкой жёстких ссылок серии используют одни и те же данные PNG, иначе PNG копируется. Если поменялась версия карты, удалите PNG из кэша для повторного захвата. **Дополнительно → Позиции на карте…** создаёт HTML с метками и ссылкой на PNG серии. Старые пути просмотра также поддерживаются.

Границы вычисляются по сетке ячеек земли из Dagor и сохраняются в метаданных. Для дополнительных изображений MRT, глубины и других буферов включите отдельно **Диагностика рендера** (`--render-debug`).

Во время пакетного рендера Dagor сохраняет записи в один журнал `metadata.pending.blk`. Успешный запуск публикует `metadata.jsonl` и удаляет журнал. После сбоя инструмент восстановления принимает как новый журнал, так и отдельные `frame-*.pending.blk` старых серий.

В COCO `images[].ke_scene` содержатся фактические `tank_world_xyz`, `tank_yaw_deg`, `camera_eye_world_xyz`, `camera_look_at_world_xyz`, `camera_horizontal_fov_deg`; ось Y вертикальна. Это дополнительные поля COCO. Отсутствующее в старых метаданных значение записывается как null; для старой серии можно заново вызвать экспорт в новую папку.

### Предполагаемая застройка

Включите **Дополнительно → Найти предполагаемую застройку** или `frame --scan-buildings`. При первом кадре Dagor выгружает X/Z и имена загруженных объектов в `scene-instances.tsv`. После рендера `urban-zones.json` перечисляет центры, границы и количество предполагаемых зданий в нескольких зонах. Эвристика группирует соседние ячейки размером 128 мировых единиц, если в каждой найдено минимум три позиции объектов с именами зданий. Пустой результат может означать другую схему имён или неполное покрытие загруженными объектами. Центры зон предназначены для проверки в редакторе. Автоматического размещения и городской квоты пока нет.
