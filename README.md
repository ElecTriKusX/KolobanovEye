# KolobanovEye 2.0

Локальный генератор синтетических RGB-изображений и COCO-аннотаций для детекции танков (`tank`) на ресурсах War Thunder с использованием открытых исходников Dagor Engine, CDK и закреплённого OOZ.

**Диагностика 19.11.2026:** дамп и совпадающий PDB подтвердили нарушение stack cookie внутри декодера OOZ (`daKernel-dev.dll`). Защита локального C++ OOZ больше не приводит к этому crash, но карта `avg_abandoned_factory.bin` по-прежнему возвращает `ooz: decode failed` (Leviathan). Теперь генератор сохраняет первый проблемный блок локально для автономного анализа; подробности — в [отчёте об инциденте](docs/incident-2026-11-19-dakernel-ooz.md). **Это ещё не исправление декодера:** успешно загрузить карту на Windows предстоит.

**Текущая ветка:** [feature/avg-map-catalog-whitelist](https://github.com/ElecTriKusX/KolobanovEye/tree/feature/avg-map-catalog-whitelist). **Пока не сливать в `main`: последовательная обработка нескольких карт в одном DaEditor требует реального Windows/DX11-теста.**

## Как устроена генерация

1. В GUI выбираются **одна или несколько карт** в белом списке `avg_*.bin`, число кадров, seed, параметры камеры, танка и среды. Отдельного выбора «Текущий запуск» нет.
2. `ke_single_editor.py` распределяет квоты кадров по выбранным картам и создаёт **одну очередь** `probe.dcmd` для одного запуска `daEditor3x-dev.exe`.
3. DaEditor загружает первую карту, рендерит все её кадры, освобождает ресурсы уровня, загружает следующую карту **в том же процессе**, повторяет прогрев и продолжает до завершения очереди.
4. RGB сразу записываются в строящийся `dataset/raw/images`, а все метаданные по завершении собираются в **один** `dataset/raw/annotations/instances.json` (COCO). Технический `dataset/runs/run-...` не содержит второго набора изображений или COCO.
5. GUI «Провести анализ» **отдельно, по запросу** создаёт `dataset/analysis/index.html` и карты с точками расстановок танков. Генерация сама эту папку не создаёт.

В случае неудачного рендера/валидации прежний `dataset/raw` остаётся неизменным. GUI спрашивает подтверждение перед заменой последнего результата. Историю технических запусков в `dataset/runs` пользователь очищает самостоятельно. Всё `dataset/`, кроме README, исключено из Git.

## Проверка отказа OOZ без многократного запуска DaEditor

Если `avg_abandoned_factory.bin` не загружается с `ooz: decode failed`, после новой сборки `kolobanoveye.py build` и одного запуска GUI в техническом `dataset/runs/run-.../ooz-failures/` появятся локальные `failed-ooz.bin` и `failed-ooz.txt`. Они не добавляются в Git. `host-stdout.log` дополнительно содержит `OOZ_STEP_FAIL`, `OOZ_QUANTUM_FAIL` и `OOZ_LEVIATHAN_LZ_TABLE_FAIL` при соответствующей ошибке.

Без запуска DaEditor можно воспроизвести декодирование именно той же C++ библиотекой:

```powershell
python -m tools.ke_ooz_replay
```

Для независимой проверки Rust `oozextract` версии 0.5.7 (необязательно, устанавливается локально):

```powershell
winget install -e --id Rustlang.Rustup
# Откройте новую Developer PowerShell, чтобы cargo попал в PATH
cargo install oozextract --version 0.5.7 --locked --features cli,verbose_errors --root D:\Projects\ke-decoders
python -m tools.ke_ooz_replay --unoodle D:\Projects\ke-decoders\bin\unoodle.exe
```

Если Rust успешно распакует тот же блок, а C++ нет, это обоснование для отдельной замены декодера внутри **того же** процесса DaEditor. До такой проверки рабочий backend не переключается на неподтверждённую альтернативу.

**Не публикуйте `failed-ooz.bin` в GitHub:** он содержит фрагмент ресурсов War Thunder. Для диагностики достаточно текстового вывода команды и `host-stdout.log`.

## Запуск в Windows Developer PowerShell x64

```powershell
cd D:\Projects\KolobanovEye
git fetch origin
git switch feature/avg-map-catalog-whitelist
git pull --ff-only origin feature/avg-map-catalog-whitelist

python -m unittest discover -v

# OOZ закрепляется один раз, если ещё не перенесён в vendor/ooz
python -m tools.vendor_ooz

# После первоначального закрепления OOZ внешний D:\Projects\ooz не нужен
python .\kolobanoveye.py build --dagor D:\Projects\DagorEngine
python .\ke_gui.py
```

Если ранее был установлен OOZ в `vendor/ooz`, повторное выполнение `python -m tools.vendor_ooz` не требуется. [Подробнее о закреплённом декодере](vendor/README.md).

Запуск без GUI:

```powershell
python .\ke_generate.py --config .\config.example.json

# Если нужно заменить уже существующий dataset/raw:
python .\ke_generate.py --config .\config.example.json --replace-raw

# Анализ после успешной генерации:
python -m tools.ke_analysis --dataset .\dataset
```

**Обязательно:** `D:\Projects\DagorEngine` должен быть локально собран по закреплённой ревизии `9639942de5a8e5b01d91977f60ed82cda22d5f41`; для DX11 нужен запущенный Windows-сеанс. Компиляция C++ после последних изменений и переход между двумя реальными картами пока не подтверждены.

## Что в интерфейсе

В основной форме: пути к Dagor и War Thunder, количество кадров, количество ракурсов на позицию, размеры/FOV, ракурсы и высота камеры, азимут корпуса, диапазоны башни и ствола, отступ от краёв танкового поля, высота рельефа и параметры прогрева. Режимы расположения: **«Танковое поле»** и **«Вокруг точки»**. Режим «Весь ландшафт» удалён из рабочего интерфейса.

Основные действия: «Карты / белый список», «Создать и проверить датасет», «Провести анализ», «Открыть папку» (всегда доступна), «Копировать журнал». В дополнительных настройках сохранены стабилизация изображения/неба, отладочный рендер и импорт/экспорт JSON-параметров.

Ручные диагностики `last_clip`, рельефа, восстановления метаданных и старые кнопки внешнего COCO, позиции на карте, справки и поиска застройки удалены из GUI. Низкоуровневая диагностика исходников может сохраняться в отдельных инженерных инструментах, но не входит в основной pipeline.

## Уже реализовано и ограничения

- Загружались реальные Normandy и Tiger H1, генерировались RGB и приблизительные рамки из проекции 3D AABB; ранее подтверждён адаптивный прогрев, устранивший визуальную пелену на проблемных ракурсах.
- Поворот башни и наклон орудия Tiger H1 используются в разметке с консервативной рамкой. Позиции и параметры камеры фиксируются в метаданных; объекты всё ещё относятся к одному классу `tank`.
- Границы танкового поля берутся из `tankMapCoord0/1` уровня, по ним рассчитывается вписанный квадрат. Обзорное изображение этого квадрата рендерится средствами Dagor отдельно от обычного RGB.
- Корректность геометрии контакта гусениц, коллизий со зданиями, видимого силуэта и amodal bbox не гарантирована. Рамки приближённые. Погодные вариации, несколько моделей/танков, отрицательные кадры и сегментационные маски пока отдельные этапы полного ТЗ.
- Разделение на train/val/test, поиск утечек похожих сцен и публикация датасета **не входят в текущую реализацию**. `raw` остаётся одним несегментированным набором.
- Windows/DX11-проверка **новой** однопроцессной многокартовой схемы ещё обязательна. Python unit/integration tests моделируют DaEditor и не доказывают корректность реального рендера.
