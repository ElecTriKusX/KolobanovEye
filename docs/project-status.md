- По приложенному пользователем архиву `build-logs (2).zip` установлена точная причина падения Jam: `strmLevel.cpp(1103,1107,1108)`, `no member named 'getTex2D' in 'resptr_detail::ResFactory<BaseTexture>'`. Декодер `ke-ooz.lib` уже собрался успешно, ошибок OOZ-компиляции нет.
- Исправлено: новая версия `engine/patches/dagor-tank-map-render.patch` объявляет объект целевого текстурного рендера как `UniqueTex target`, а не `auto target`. Функция `upgrade_roi_unique_tex()` в `kolobanoveye.py` обновляет ровно одну декларацию в **уже пропатченном** Dagor без `git reset`; повторное применение идемпотентно.
- OOZ закреплён для **локального** использования в `vendor/ooz/` через `python -m tools.vendor_ooz`. Источник — пять уже скомпилированных decode-only файлов `build-logs/ooz-local`, SHA-256 — `vendor/ooz.lock.json`, исходный коммит `05038060aa68f9187ae9923b2388ca8db40e58d1`. `build` без `--ooz` умеет автоматически использовать такую копию.

## Текущая архитектура 18 ноября 2026 — ОДИН DaEditor

**Утверждённое пользователем правило:** один процесс `daEditor3x-dev.exe` на весь пользовательский запуск. Одна карта → все её запланированные кадры → освобождение уровня → следующая карта в том же процессе. Ни «отдельный процесс на карту», ни отдельная папка запуска для каждой карты не допускаются.

**Реализовано кодом в ветке:**

- `ke_single_editor.py` (вместо удалённого `ke_multi_generate.py`) вычисляет детерминированные квоты, создаёт `capture/*.blk` и `plans/*.json` на карты, одну очередь `probe.dcmd` и один вызов `daEditor3x-dev.exe`.
- Проведено чтение исходников Dagor: `BinSceneViewPlugin::loadKolobanovEyeLevel()` вызывает `AcesScene::loadLevel()`; тот вызывает `clear()` и загружает новую карту, а `ConBatch` обрабатывает несколько команд и останавливает очередь при неуспехе. Указанные API исследованы, не придуманы.
- Новые идемпотентные C++ миграции для ранее пропатченного Dagor: `enable_batch_tank_map_output` создаёт отдельное обзорное PNG на каждый загруженный уровень; `reset_level_settings_on_reload` очищает `levelSettingsBlk`; `preserve_landmesh_renderer_release_on_reload` не позволяет потерять указатель на предыдущий `lmeshRenderer` до `clear()`. Windows-компиляция и тест ресурсов **ещё не пройдены**.
- `ke_dataset.py` создаёт кадры сразу во временном `dataset/.raw-staging-*/images`. После успешного завершения читает journals, валидирует все кадры и сохраняет единственный COCO `raw/annotations/instances.json` плюс все метаданные. Только тогда заменяет `raw`; старый сохраняется при ошибке.
- `dataset/runs/run-...` теперь один технический проект/лог на весь запуск с `capture/`, `plans/`, `maps/`, `journals/`, `probe.dcmd`. Убраны дублирующие `coco/`, `images/` и вложенная `runs/<map>`.
- GUI `ke_gui.py`: удалены «Справка», отдельная «Текущий запуск», whole_map, отдельный COCO, ручной last_clip, сканер застройки, ручные проверка серии/рельефа/восстановление и старые «Позиции на карте». В списке должно быть выбрано ≥1 доступной карты; «Открыть папку» всегда включена.
- Добавлена отдельная кнопка «Провести анализ», `tools/ke_analysis.py`: создаёт `dataset/analysis/index.html`, HTML-карты с точками уникальных позиций танков из метаданных `raw` поверх обзорных PNG соответствующего технического запуска. Сведения об X/Z берутся из сохранённых BLK; ориентация обзора на Windows пока требует калибровки.
- Из исходников удалены `tools/ke_urban.py`, `tools/ke_map.py`, `tools/ke_terrain_audit.py`, `tools/ke_recover.py` как наследие старого GUI, вместе с их устаревшими тестами. Инженерные проверки PNG/bbox/frames сохранены во внутреннем потоке.

**Тестовое подтверждение:** GitHub Actions проверяет тесты Python, в том числе офлайн имитацию двух карт в **одном** вызове редактора, формат папок и создание анализа по запросу, а также синтаксис и применимость ROI-патча к закреплённой ревизии исходников. **Это не заменяет сборку Windows и реальную смену карт / GPU ресурсов.**

**Ближайшая приёмка:** сборка Dagor в Developer PowerShell x64, 1 карта × 2 кадра, затем 2 карты × 2 кадра в одном DaEditor, проверка 2 `MAP_BEGIN` / `SEQUENCE_OK` в едином `.logs/.../debug` (сообщения `CON: [KE]`), оба обзорных PNG в `runs/.../maps`, 4 RGB и один COCO в `raw`. Нажать «Провести анализ» и сверить позиции. Если нет `BUILD_OK` и успешного DX11, в `main` не сливать.

## Авария нативного редактора до первой карты — 19 ноября 2026

Архив `.logs(4).zip` содержит `debug`, `logerr`, `logwarn`, `last_debug`, без native stack или `fatalerr`. Наблюдения:

- В 97.65 с DaEditor записано `daEditorX has loaded and ready for interaction`; затем `start async batch: .../probe.dcmd` и `CON: exec command 'wait.frame 8'`.
- Последняя строка `97.85 [D]` не содержит текста. НЕТ `MAP_BATCH_BEGIN`, `MAP_TASK_BEGIN`, `MAP_BEGIN`. Исполнение native C++ `kolobanoveye.batch` **не началось**. Код Windows — `0xC0000409`; определить модуль/стек исключения только по архиву нельзя.
- Консольная очередь уже содержит единственную `kolobanoveye.batch`, поэтому гипотеза о размере очереди не объясняет повторное падение. Возможный риск — первый idle/render tick при ожидании кадров до загрузки карты; он не подтверждён как первопричина.
- Из `ke_single_editor.py` удалена первая `wait.frame 8`. Теперь первая консольная команда — `kolobanoveye.batch`. Изменение **только Python**, без повторной сборки Dagor.
- Диагностика `editor_failure()` теперь игнорирует пустые строки native debug вида `97.85 [D]` и выводит последнюю содержательную запись/последнюю `CON: exec command`.
- Проверка: один уровень × 2 кадра из GUI на обновлённой ветке. Если crash повторяется до `MAP_BATCH_BEGIN`, получить Windows Application Event ID 1000/1001 и, при необходимости, WER minidump — дальнейшие C++ фиксы без стека не обоснованы.

Нельзя объявлять данный crash исправленным по одной успешной CI-проверке; только повторный запуск в Windows покажет фактический результат.

## Дамп daKernel / Kraken, 19 ноября 2026

По дампу `daEditor3x-dev.exe.40732.dmp` и точно совпавшему `daKernel-dev.pdb` установлено: исключение `0xC0000409`, подтип `0x2 = FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`, адрес `daKernel+0x183FD1 = __report_gsfailure+0x1D`. В сохранённом стеке есть адреса `Kraken_DecodeMultiArray`, `Leviathan_ReadLzTable`, `Kraken_Decompress`, `oodle_decompress`, `OodleLoadCB::decodeData`. Проверен исходник закреплённого OOZ: `num_arrays_in_file &= 0x3f` допускает значение до 63 при размере двух локальных массивов всего 32, без проверки перед индексированием. **Конкретно это повреждение стека в данном прогоне не доказано**, но дефект реален.

Установлено, что поле `num_arrays_in_file` содержит шесть бит (0–63). Ранее внедрённая проверка `> 32 → return -1` останавливала повреждение стека, но могла отвергать допустимые потоки. Теперь сборочная копия использует два локальных массива по **64 элемента**, полностью покрывая диапазон счётчика. Исходники `vendor/ooz` и исходный `build-logs/ooz-local` не меняются. Собирается в `build-logs/ooz-compiled` с MSVC `/Z7` для строк отладки. [Подробное расследование](incident-2026-11-19-dakernel-ooz.md).

**Статус:** Python CI успешно, Windows компиляция и проверка генерации после защитного патча ожидаются. Без них не считать проблему исправленной и не сливать ветку в `main`.

## 19 ноября 2026 — автономная диагностика Leviathan

На `avg_abandoned_factory.bin` после успешной Windows-компиляции расширенных до 64 элементов массивов декодер `powzix/ooz` всё равно возвращает `-1` (type=12, packed=3630624, unpacked=13009598). По архиву `daEditor3x-dev.exe-2026.11.19-16.51.53.zip`: редактор успешно запустил `kolobanoveye.batch`, зафиксировал ошибку Oodle, остановил пакет и **штатно завершился с кодом 0**. Не было `MAP_OK`, `MODEL_OK` и готовых RGB кадров. Сообщение `WTF? Uncatched exception` также присутствует в `logerr` при откате загрузки уровня, однако это не crash типа `0xC0000409`. Массовый вывод сообщений об отсутствующих shader variables и другие предупреждения не являются подтверждённой первопричиной.

Для детерминированного расследования в ветку добавлены:

- `enable_failed_ooz_stream_capture()` — идемпотентная C++ миграция Dagor, сохраняющая только первый отказавший OOZ-блок до 16 MiB в `run/ooz-failures/failed-ooz.bin` и его `failed-ooz.txt` (метаданные о размере/кодеке). Включается `KE_OOZ_FAILURE_DIR` только для процесса генерации; в Git файлы не попадают.
- `trace_kraken_failures()` — failure-only телеметрия о смещении decoded byte offset, размере quantum и сбоях `Leviathan_ReadLzTable`, в `host-stdout.log`.
- `tools/native/ke_ooz_replay.cpp` — `ke-ooz-replay.exe`, собираемый через MSVC вместе с тем же `ke-ooz.lib`, что используется в `daKernel`. `python -m tools.ke_ooz_replay` использует сохранённые данные без открытия DaEditor.
- Для независимого A/B сравнения на тех же байтах `python -m tools.ke_ooz_replay --unoodle .../unoodle.exe` запускает локально установленный `oozextract 0.5.7` (MIT). По публикациям пользователей декодер применялся к ресурсам War Thunder, но конкретный блок здесь ещё **не проверен**.
- Регрессионные тесты точных C++ миграций, проверки метаданных и обеих ветвей автономного воспроизведения.

**Статус:** Python CI проходит. Windows сборка новых C++ диагностик и сам A/B тест пока ожидаются. Основной декодер остаётся прежним; однопроцессная архитектура DaEditor неизменна. До реального успешного рендеринга и двухкартового теста `main` не изменять.


## Антивирусное обнаружение и возобновление сборки — 19 ноября 2026

Пользователь прислал протокол `Вставленный текст(3).txt`: Windows x64 Developer PowerShell, 93 Python-теста прошли; `kolobanoveye.py build` успешно скомпилировал `kraken.obj`, `ke-ooz.lib`, `ke-ooz-replay.exe`, запустил Jam для DaEditor и был прерван вручную (`KeyboardInterrupt`) до `[KE] BUILD_OK`. Вторая попытка ошиблась на `git apply --check` для `dagor-ooz.patch`: файл `oodleIoOoz.cpp` уже существовал, но обратная проверка патча провалилась, потому что постпатчевое `enable_failed_ooz_stream_capture` изменило исходный C++ файл. Это ошибка идемпотентности нашей обвязки, **не** основание сбрасывать или очищать локальный Dagor.

Событие Kaspersky File Antivirus: обнаружение `VHO:Trojan.Win32.Agent.gen` (эвристика, высокая опасность) при линковке **`build-logs/ooz-compiled/ke-ooz-replay.exe`**, MD5 `B5797152ED80A29AD81E464805F82A84`, процесс `link.exe` из каталога MSVC. Нельзя утверждать, что срабатывание ложное или что остальные результаты сборки безопасны. Не восстанавливать подозрительный исполняемый файл, не добавлять исключения, не отключать антивирус. Не проверено, что именно удалило `daEditor3x-dev.exe`; прерванная сборка достаточна для объяснения отсутствия файла, но журнал карантина надо проверить и для редактора.

В ветке реализовано:
- `ooz_patch_installed(dagor)` проверяет наличие согласованной интеграции OOZ по декодеру и Jamfile, включая после диагностической C++ миграции. Если она уже есть, повторно `git apply` не выполняется. При неполном состоянии выбрасывает ошибку, не перезаписывает чужой код и не применяет обходных вариантов.
- Автоматическая линковка и проверка `ke-ooz-replay.exe` исключены из `prepare_ooz()`. Сборка `ke-ooz.lib` и рабочей `daKernel` сохранена. Необходимо дождаться результата проверки антивируса, прежде чем запускать любые подозрительные исполняемые артефакты.
- Тесты для чистого Dagor, полной OOZ интеграции, повторного применения после capture migration и частичных/неизвестных исходников.

**Приёмка:** обновить ветку, собрать под включённым антивирусом без `ke-ooz-replay.exe`, не прерывать Jam до `BUILD_OK`. Если срабатывание повторится на другом файле — прекратить выполнение и анализировать событие; не добавлять исключения. Дополнительно проверить `editor-ooz.log` и журнал карантина. Текущую ветку в `main` не сливать.

## 19 ноября 2026 — 1–2 карты подтверждены, четвёртая падает на атласе теней

Реальная Windows-проверка **успешна для 1 карты × 6 кадров и 2 карт × 10 кадров** в одном DaEditor. Обе завершились `SINGLE_EDITOR_OK` и `DATASET_RAW_OK`. Базовая последовательная смена карт доказана. Запуски 60 карт / 310 кадров и 20 карт / 200 кадров завершились кодом редактора 1.

По пользовательскому архиву `.logs(6).zip`, относящемуся **только к 20-картовому запуску**, первые три карты и 30 кадров готовы, а `avg_alaska_town.bin` стала четвёртой и завершилась native fatal: `validateUpdateSubRegion.h:22`, `subres=7 → slice=1`, а у `tree_fagus_hurtgen_pl_l_a_s` всего один слой атласа. Стек: `BcCompressor::copyToMip` → `ImpostorTextureManager::update_shadow` → `AcesScene::beforeRender`. Это **не OOZ** и **не стек-cookie fast-fail**. Warning'и сообщают несовпадение палитр поворота, экспортированных в карту, и текущих растительных ресурсов (1 против 3), но конкретную причину ресурсов пока нельзя утверждать.
